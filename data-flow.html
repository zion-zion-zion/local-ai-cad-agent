Source-grounded runtime map

一次 Prompt 如何变成可验证的 CAD 模型

当前实现不是一次性文本生成，而是“完整上下文 + 工具调用 + 本地 CAD 内核反馈 + 视觉复核”的多轮循环。

模型 gpt-5.6-luna 推理 high 循环上限 120 接口 OpenAI-compatible 本地模型 未启用
1. Browser输入 prompt、上传图片、接收 SSE、加载 STL
2. Flask/api/chat 接收并保存输入，后台启动 AgentRunner
3. Context系统提示词、历史、约束、图片、工具 schema
4. LLM/chat/completions 流式返回文本、推理和 tool call
5. Local CAD工具执行、Bubblewrap、build123d、指标和渲染

CAD 结果和渲染图会回到 Context，然后进入下一轮 LLM 请求。

关键结论：每一轮都会重新发送系统提示词和当前完整的有效消息历史；接口没有只发送“本轮增量”的逻辑。

首次请求：模型实际收到什么

浏览器提交的是 multipart FormData，服务器先返回 HTTP 202，再由后台线程调用模型。没有图片时，第一次请求的核心结构如下：

system
<完整系统提示词，约 40,570 字符>
<identity>You are a pragmatic local CAD assistant using build123d.</identity>
...
<build123d_cli_playbook>...</build123d_cli_playbook>
user
创建一个 60 × 30 × 4 mm 的安装板，并开四个 M3 孔。

有图片时，当前 user message 的 content 是 text part 和 image_url part 的数组，图片被编码为 data:image/png;base64,...。模型收到图片内容，不是 inputs/ 本地路径。

POST https://api.claudecode.net.cn/api/codex/backend-api/codex/v1/chat/completions
Authorization: Bearer <API key>
Content-Type: application/json

{
  "model": "gpt-5.6-luna",
  "messages": [
    {"role": "system", "content": "<完整系统提示词>"},
    {"role": "user", "content": "用户原始 prompt"}
  ],
  "stream": true,
  "stream_options": {"include_usage": true},
  "tools": ["11 个 function schema"],
  "reasoning_effort": "high"
}

系统提示词的组成

系统提示词由静态规则和完整 build123d playbook 拼接而成。代码会根据 playbook 的 mtime 自动刷新缓存。

静态 Bundle：身份、设计原则和操作规则

identity 你是使用 build123d 的本地 CAD 助手。

design_principles 优先材料高效、紧凑和最简单的满足需求的几何；参考图只用于比例，不无故放大结构。

operational_rules 只能编辑 model.py 和 summary.md；参数放在顶部；每次模型修改后调用一次 cad_build_and_verify；成功后更新 summary；Final export 由 UI 执行。

build123d_rules 使用结构化 CAD 错误修复；验证实体、尺寸和渲染；处理 fillet/chamfer、拓扑索引、RadiusArc、Ellipse、feature marker 和保护约束。

constraint_rules 保护 pin 由系统强制执行，模型不能创建、删除或修改 pin。

experience_memory 可以搜索和保存已验证的 build123d/CAD 修复经验，不保存完整对话、个人数据、源码或长 traceback。

嵌入的 build123d CLI Playbook

当前 playbook 为 875 行、约 36 KB，包含执行契约、参数化建模、基础 API、拓扑选择、15 个完整示例、常见错误修复、策略指南和 pre-flight checklist。

模型因此会看到 result 变量约定、毫米单位、Builder/Algebra 模式、Box/Cylinder/Hole/Sketch/Extrude/Revolve/Sweep/Loft 等具体 API 约束，而不是只依赖训练记忆。

运行时追加的约束消息

如果项目存在用户保护项，系统会在历史之后、当前 prompt 之前加入：

<runtime_active_constraints>
Protected (do not change):
- parameter: HOLE_DIAMETER
- source_feature: base_plate
</runtime_active_constraints>

工具 Schema：模型可以请求什么

工具定义在请求顶层的 tools 字段中，不是 system prompt 的正文。当前模型可见的工具如下：

工具模型参数执行结果
file_readfilename: model.py / summary.md文件文本
file_writefilename, contentAST 检查、约束检查、revision、写入结果
file_replacefilename, old, new第一处精确替换
file_regex_replacefilename, pattern, replacement, count受限正则替换
cad_build_and_verify无参数几何指标、preview.stl、render.png
terminal_runPython 脚本参数、timeout_secondsreturncode、stdout、stderr
terminal_check只读 Python/pytest/pip 检查参数检查输出
questiontitle、questions 数组浏览器表单，Agent 暂停
experience_searchquery最多 5 条历史经验
experience_addproblem、solution、tags写入跨项目经验库
experience_updateid、可选更新字段更新经验记录

模型返回和下一轮消息

模型可能返回普通文本，也可能返回 tool call。流式响应中的函数名和 arguments 会被分片，客户端按 tool-call index 拼接后再执行。

{
  "role": "assistant",
  "content": null,
  "tool_calls": [{
    "id": "call_abc123",
    "type": "function",
    "function": {
      "name": "file_write",
      "arguments": "{\"filename\":\"model.py\",\"content\":\"...\"}"
    }
  }]
}

执行成功后，下一轮会把 assistant tool call 和对应的 tool message 一起发回模型：

{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "{\"ok\":true,\"tool\":\"file_write\",\"data\":\"Wrote model.py ...\"}"
}

模型会收到

  • 完整 system prompt
  • 当前及最近历史 user/assistant/tool 消息
  • 工具执行结果
  • 当前请求中的图片
  • 成功 CAD 后的 render.png
  • 运行时保护约束

模型不会自动收到

  • API key
  • conversation.jsonl 原始文件
  • 浏览器界面状态
  • STL 二进制内容
  • quality 目录完整记录
  • Finalize 报告生成过程

Agent 循环：按时间顺序

01
初始化 ProjectTools

加载 revision、约束、文件、终端、CAD、提问和经验工具；恢复或校准已有 model.py。

02
建立 messages

读取 api_messages.jsonl，最多保留 100 条；加上系统提示词、运行时约束和本次 user prompt。

03
调用 LLM

POST /chat/completions，stream=true；SSE 中的文本、reasoning 和 tool call 实时推送到浏览器。

04
执行 tool calls

解析 JSON arguments，逐个执行；每个调用都生成 tool_status，并把统一 JSON envelope 加入 messages。

05
成功 CAD 后视觉复核

把指标和 render.png 作为新的 user message 追加，要求模型检查缺失、错位和不合理几何。

06
判断是否继续

有错误就修复；model.py 修改后重新 build；没有新预览时系统会提示一次必须调用 cad_build_and_verify。

07
浏览器确认预览

成功构建后浏览器加载 STL，POST preview/displayed；确认后才发布最终 assistant message。

循环上限：当前配置为 120 次 Agent 循环。一次模型响应可以包含多个 tool call，因此 120 次循环不等于 120 个工具调用。

cad_build_and_verify 内部做什么

执行

  • 读取 model.py
  • 再次做 AST pre-flight
  • 复制到临时目录
  • 通过 Bubblewrap 沙箱运行 runner.py
  • 网络和危险系统调用受限
  • 超时为 120 秒

验证

  • 读取顶层 result
  • 计算 solids、volume、bounding box
  • 检查 is_valid、有限数值和正尺寸
  • 导出 preview.stl
  • tessellate 后生成 512 × 512 render.png
  • 记录当前 revision 的 build 状态
{
  "ok": true,
  "tool": "cad_build_and_verify",
  "data": {
    "metrics": {
      "solid_count": 1,
      "is_valid": true,
      "volume_mm3": 6800.0,
      "dimensions_mm": {"x": 60.0, "y": 30.0, "z": 4.0}
    },
    "preview": "preview.stl",
    "render": "render.png"
  }
}

不同分支

CAD 成功
保存 preview.stl 和 render.png，发布 preview_updated；追加视觉审查消息；模型可以继续修复或结束；浏览器加载预览后，Agent 才发布完成消息。
CAD 失败
返回带 code、phase、message、retryable、hint 的错误 envelope；模型读取错误并修改 model.py。若最终没有产生新预览，系统发布 agent_error，不会伪装成完成。
模型调用 question
问题通过 SSE 显示在浏览器，写入 .agent_state.json，Agent 暂停。用户回答经过输入类型校验后，被格式化成新的 user message，重新启动 Agent。
模型没有调用任何工具
如果这是纯聊天，会直接完成；如果之前已经使用过工具但没有生成新 CAD 预览，系统会先追加“model.py exists but it has not been verified. Call cad_build_and_verify now.”，再给模型一次机会。
用户点击 Stop
设置 stop event，终止模型请求、终端进程或 CAD 进程，清理等待问题和 pending preview，并通过 SSE 通知浏览器。

Finalize：最终导出

Finalize 是独立的本地处理流程，不是又一轮 LLM prompt。它重新执行当前 model.py，生成最终渲染和 STEP/STL，然后根据 summary.md 与 conversation.jsonl 生成 report.md，并保存当前源码 SHA 以识别过期导出。
